# Actions Lock File Specification

This document is the authoritative specification for how the action uses the
`gh actions-lock` lock file (`.github/workflows/actions.lock`) and `$/`
references. The implementation lives in `src/lockfile.ts` and
`src/workflow-parser.ts`; the tests in `__tests__/lockfile.test.ts` and
`__tests__/lockfile-verify.test.ts` assert each rule. Any change to this
behavior must update this document and the tests together.

## Lock file format

The lock file is generated by
[`gh actions-lock`](https://gh.io/actions-lockfile) and must not be edited by
hand.

```yaml
version: 'v0.0.3'
workflows:
  '.github/workflows/ci.yml':
    - 'actions/checkout@v4'
dependencies:
  'actions/checkout@v4':
    ref: 'v4'
    commit: 'sha1-<40 hex characters>'
    owner_id: 1
    repo_id: 2
    hostname: 'github.com' # optional: see below
    uses: [] # optional: lock keys of transitive dependencies
```

- `workflows` maps repository-relative workflow paths (with `/` separators) to
  the `uses` they contain. Only workflows listed here are governed by the lock.
- `dependencies` keys are canonical `owner/repo@ref`, without an action or
  workflow subpath. Lookups for `owner/repo/path@ref` fall back to this key.
- `commit` may pin a commit that differs from the current target of `ref` (e.g.
  `@main` may have moved since locking). The locked commit is authoritative.
- `hostname` (v0.0.3) states where the dependency is resolved. It is carried on
  the dependency as its route, so fetching, `$/` pinning, remote lock lookups
  and fork/tag resolution all use it, and it never alters the probing cache used
  for unlocked entries.
  - `github.com`: public GitHub only, never the home host. On a tenant without a
    `public-github-token` a warning is logged and the contents are treated as
    unfetchable (see below).
  - Omitted: the home host of the workflow owning the lock only (no fallback to
    github.com). For a callable workflow's own lock that is the host the
    workflow was fetched from, so a workflow fetched from github.com keeps its
    unqualified entries on github.com.
  - Locks older than v0.0.3 carry no hostname; their pins are github.com's, so
    every entry is treated as `github.com`.
  - Entries that are not in the lock keep the heuristic: home host first, then
    github.com when a `public-github-token` is available.

## Loading and verification

| Situation                                                                                     | Behavior                                                                                     |
| --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| No lock file                                                                                  | Old behavior (resolve by ref). `gh` is never invoked, even if `actions-lock-version` is set. |
| Lock file malformed                                                                           | Fail the workflow.                                                                           |
| `gh` or the extension unavailable / not installable                                           | Log a warning and use the lock file unverified.                                              |
| As above, but `actions-lock-version` is set                                                   | Fail the workflow.                                                                           |
| `gh actions-lock --verify` fails for any reason (rejection, timeout, authentication, network) | Fail the workflow.                                                                           |
| `gh actions-lock --verify` succeeds                                                           | Use the lock file.                                                                           |

A lock file is malformed when it:

- is not a YAML mapping;
- has a missing or empty `version` (the value itself is not checked);
- has a `dependencies` value that is not a mapping;
- has an entry whose `commit` is not `sha1-<40 hex characters>`.

### Extension management

- `gh --version` is used to detect the GitHub CLI.
- `gh extension list` (tab separated: name, repository, version) is used to
  detect `github/gh-actions-lock`; it has no `--json` output.
- Without `actions-lock-version`, an installed extension is used as-is and a
  missing one is installed at its latest release.
- With `actions-lock-version`, a different installed version is removed
  (`gh extension remove actions-lock`) and the requested version installed
  (`gh extension install github/gh-actions-lock --pin <tag>`).

## Lock scope

- The repository lock governs only workflows listed in its `workflows` map.
- Everything else is resolved by ref (old behavior) and logged as not covered:
  workflows in other folders, a root `action.yml`, and files found through
  `additional-paths`.
- Local composite actions inherit the scope of the workflow that references
  them.
- Local callable workflows (`uses: ./.github/workflows/x.yml`) get their own
  scope, based on whether the lock covers them.
- When the same local file is reached from both a locked and an unlocked
  context, it is processed once per scope and both dependency sets are
  submitted. They may produce different dependency graphs.
- Remote actions are tracked per (dependency, lock state) for the same reason.
- Composite actions found through `additional-paths` also have their remote
  transitive dependencies resolved.

## Remote callable workflows

Callable workflows in a different repository always use their own context:

- Their own lock file is fetched at the resolved commit, but only when the
  repository being scanned has a lock file.
- It is used only if its `workflows` map covers that workflow path.
- Without such a lock, their dependencies are resolved by ref.
- The caller's lock is never used for them, including when the workflow file
  cannot be fetched.
- A malformed lock file in a callable workflow, at any nesting depth, fails the
  workflow.

## Unfetchable remote actions

When a locked remote composite action cannot be fetched, its dependency graph is
recovered from the `uses` entries in the lock file, recursively. This never
applies to callable workflows (see above).

## `$/` references

- `$/path` refers to the repository that contains the referencing file.
- In the scanned repository it resolves from the repository root. The resolved
  path must stay inside the repository.
- In a remote action or workflow it resolves to the same `owner/repo` at the
  parent's resolved commit.
- If the parent ref is locked, the locked commit is used.
- If the parent ref is movable and unlocked, it is first resolved to a commit
  SHA through the API so all children come from the same commit. If that fails,
  a warning is logged and children resolve through the movable ref; unlocked
  refs resolve to whatever they point to at scan time.

## Submission

- Locked dependencies are submitted with their ref replaced by the locked commit
  SHA. The `uses` string is kept as the lock lookup key.
- No extra metadata is added to the submission to mark lock usage.
- A package URL reported by both a locked and an unlocked usage is simply
  submitted once.

## Fork resolution

Fork resolution is unaffected by the lock file. A forked action used in a
workflow appears in the lock file under its own name; the original repository is
reported only for vulnerability linking.
